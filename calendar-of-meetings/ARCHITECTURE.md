# Архитектура

Описание состояния проекта на конец функциональности ролей (админ/гость):
календарь встреч с персистентным бэкендом. Документ отвечает на вопрос «как
устроено и почему», а не «как запустить».

- Команды, соглашения и ловушки Mantine — в [`AGENTS.md`](./AGENTS.md).

Проверено на: 53 файла в `src/` (плюс сгенерированные `src/lib/api-gen/`),
15 файлов в `server/`, 223 теста в 24 файлах, `npm run check` и `npm run build`
зелёные. Стек: React 19, Mantine 9.6.3, dayjs, TypeScript 6 со `strict`,
Vite 8, vitest 4, oxlint, Express 5, better-sqlite3 12, TypeSpec 1.11,
клиентский SDK — `@hey-api/openapi-ts` 0.95.

## 1. Что это

Одностраничное приложение + собственный серверный процесс: календарь встреч,
целиком закрытый паролем (Q12a): без входа видна только форма логина. Вошедший
гость проходит степпер «Тип → Время → Готово» (F7, D4): выбирает тип встречи,
день в пределах гостевого окна и свободный слот в инлайн-сетке, подтверждает
запись — она уходит по HTTP на express-сервер и хранится в SQLite — поэтому
переживает перезапуск, а дубль слота отклоняется сервером (слот — один
глобальный ресурс на все типы, ADR-0008). Админ попадает в
панель с двумя вкладками (F6, D4): «Типы встреч» — таблица с деактивацией
`Switch` и модалкой «Добавить тип», «Запланированные встречи» — таблица
дата/время/тип/Booker по join-DTO с сервера (S4). Компоненты и хуки видят только
абстракции `MeetingsApi`, `MeetingTypesApi`, `PlannedMeetingsApi` и `SessionApi`
(§4), смена реализации их не затрагивает.

Для локальной проверки корректности есть **дев-обход авторизации**: с
`AUTH_DISABLED=1` экран входа не нужен — роль берётся из URL (`/admin` —
владелец, остальное — гость), а сервер подставляет сессию. Это ослабление
только по конфигу: по умолчанию обход выключен, обычный вход и подписанная
сессия не меняются (`server/session.ts`, `src/lib/devRole.ts`, §5/§7).

Запросы формируют только адаптеры `http.ts` (`src/lib/meetings/`,
`src/lib/meeting-types/`, `src/lib/planned-meetings/`, `src/lib/session/`), и делают они это через
сгенерированный клиентский SDK `src/lib/api-gen` (K3, D5). SDK собран из того же
`contract/openapi.yaml` той же командой
`npm run contract`, что и остальные артефакты контракта, поэтому путь, заголовки
и тело не могут разойтись со спекой — дрейф ловит `contract:check`. Адаптеры
добавляют к вызовам SDK только то, что контракт не выражает: `credentials:
'include'` (без него браузер не подложит session-cookie, D3), прежние русские
тексты ошибок; порт `MeetingsApi` и его сигнатуры не меняются. Особый случай —
`lib/session/http.ts`: 401 от `GET /api/me` там превращается в штатное `null`
(«сессии нет»), а не в исключение. За запросами
стоит поток «репозиторий → SQLite», описанный в §3. В dev `/api`
проксируется Vite на :4000, в проде express отдаёт и API, и статику из `dist/`.

Ключевое: **Mantine не протекает наружу `components/`.** Наружу отдаются
строки `'YYYY-MM-DD'` и `'HH:mm'`, поэтому остальной код не зависит ни от версии
Mantine, ни от его внутреннего устройства.

## 3. Слои и правило зависимостей

| Слой | Файлы | Правило |
| --- | --- | --- |
| `lib/` | `date.ts`, `window.ts`, `slots.ts`, `availability.ts`, `meetings/{types,api,inMemory,http}.ts`, `meeting-types/{types,api,inMemory,http}.ts`, `planned-meetings/{types,api,inMemory,http}.ts`, `session/{types,api,inMemory,http}.ts` | Ноль React и ноль Mantine. Чистые функции и типы, тесты лежат рядом. Модули `meetings/`, `meeting-types/`, `planned-meetings/` и `session/` зеркалят друг друга и не зависят друг от друга. |
| `hooks/` | `useMeetings.ts`, `useMeetingTypes.ts`, `usePlannedMeetings.ts`, `useSession.ts` | Единственное место, которое оборачивает `lib` в React-состояние, и единственные мосты к `MeetingsApi`, `MeetingTypesApi`, `PlannedMeetingsApi` и `SessionApi`. |
| `components/` | `MeetingCalendar.tsx`, `TimeSlots.tsx`, `LoginScreen.tsx` | Только рендер. Пропсы на входе, доменных правил нет. |
| `App.tsx`, `GuestView.tsx`, `AdminView.tsx` | — | Только UI-состояние страниц (сессия и форма входа; состояние букинга; вкладки и модалка админа) и раскладка. Не импортируют `@mantine/dates`. |

Зависимости строго односторонние: `App/GuestView/AdminView → components → lib`,
`App/GuestView/AdminView → hooks → lib`.
Обратных импортов нет.

Отдельный процесс — `server/`: express-приложение, собираемое фабрикой
`createApp`, и репозиторий поверх better-sqlite3 (`createRepository`).
`rootDir: server` закрывает импорт из `src/` — варианта протечь доменное правило
на сервер нет, что и держит инвариант «домен не дублируется» (§9). Граница между
сторонами — контракт §4; на фронте ему отвечает одна реализация (`http.ts`),
на сервере — `routes.ts` + `repository.ts`. Контракт описан декларативно в
`contract/main.tsp` и генерируется в обе стороны (K1, ADR-0004); `rootDir` при
этом не трогается — серверная копия лежит внутри `server/`.

**Домен не дублируется.** «Можно ли в этот день записаться» — это
`lib/date.ts` (`isBookable`), а не проверка внутри компонента; гостевое окно
(Q5) собирается поверх — `lib/window.ts` (`isBookableDay`, `isBookableSlot`)
составляет `isBookable` и не переизобретает ни выходные, ни прошедшие дни.
«Как написать дату по-русски» — `lib/date.ts` (`formatDateRu`). Если второму
компоненту понадобится то же самое, он импортирует из `lib/`, а не переписывает
правило у себя. Расширение правила идёт в ту же функцию: к выходным добавятся
праздники и дни без свободных слотов.

**Часы — шов (T3).** Доменные правила времени не читают системные часы:
`isPast`/`isBookable` принимают `moment: string`, окно — `lib/window.ts` —
тоже, а единственным источником «сейчас» остаются `today()` и `now()` в
`lib/date.ts`, значения которых подставляют вызывающие. Границы окна и слотов
тогда тестируются фиксированной строкой `'YYYY-MM-DD HH:mm'` и не дрейфуют при
смене суток.

## 4. Контракты

Контракт API **декларативный и единый**: `contract/main.tsp` (TypeSpec, K1/ADR-0004) —
единственный источник истины. Из него генерируются `contract/openapi.yaml`, две
TS-копии (`src/lib/contract.gen.ts`, `server/contract.gen.ts`) и JSON Schema
(`contract/schema/calendar-of-meetings.json`, K4/ADR-0005); `src/lib/meetings/types.ts`,
`src/lib/meeting-types/types.ts`, `src/lib/planned-meetings/types.ts`,
`src/lib/session/types.ts`, `server/types.ts`,
`Session` и `LoginInput` — alias'ы на генерат, ручных дублей больше нет.
Копии TS две, а не одна общая, потому что `rootDir: server` закрывает серверу импорт из
`src/` (§3): копия лежит внутри `server/`, инвариант сохранён.

Всё это генерирует **одна команда `npm run contract`**, которая в конце сама же перегенерирует
артефакты во временный каталог и сверяет `diff` (`contract/check.sh`, входит в `npm run check`).
Новый генератор обязан добавить ступень и в `contract/generate.sh`, и дифф в `check.sh` —
иначе он выпадет из самопроверки.

Валидация формы переехала в **`ajv`** (K4): сервер компилирует схемы из `contract/schema/`
и прогоняет через них тело и query (`server/validate.ts`). Это булев предикат, а не резолвер —
`coerceTypes`/`useDefaults`/`removeAdditional` выключены, поэтому валидатор данные не трогает
и ничего не додумывает. Граница «формат vs домен» сохранена: `ajv` проверяет только формат,
а целостность и то, что JSON Schema не выражает, остаются рукописными в `routes.ts` (S5):
`meeting_type_id` — существующий активный тип, `booker` — из подписанной сессии, а не из
тела (Q4/C10, до 100 символов — `MAX_BOOKER_LENGTH`), и русские тексты ошибок.
Схема — один бандл (`bundleId`), объекты не
запечатаны (`seal-object-schemas` выключен), так что лишние поля по-прежнему разрешены.

Ручки API (все `/api`, кроме входа, — за сессионной cookie `session`): `POST /login`
(200/400/401), `POST /logout` (204/401), `GET /me` (200/401), `GET /meetings`
(200/400/401), `POST /meetings` (201/400/401/409). Типы встреч (S3): `GET /meeting-types`
(200/401; админу — все, гостю — только активные), `POST /meeting-types` (201/400/401/403),
`POST /meeting-types/{id}/deactivate` (200/400/401/403). Админский список (S4):
`GET /admin/meetings` (200/401/403) — join-DTO встреч с типами. Админские ручки
дополнительно требуют роль admin — иначе 403. При `AUTH_DISABLED=1` сеанс-гейт
заменяется на `devSessionGate` (§1/§5): 401 в этом режиме не бывает, а роль та же
— из URL. Порядок слоёв `server/contract.test.ts` проверяет на обычном конфиге.

Каждую операцию со стороны спеки
держит `server/contract.test.ts` (обязательный набор статус-кодов), а соответствие
`.tsp` — `contract:check`. Тот же тест сверяет и **роуты со спекой**: интроспектирует
`createRoutes(...).stack`, разворачивает Express-пути в форму OpenAPI (`:id` → `{id}`)
и проверяет, что каждая смонтированная пара «путь + метод» описана в спеке. Направление —
**роуты ⊆ спека**: контракт опережает сервер (так SDK собрал ручки S4 и S3 заранее),
поэтому лишняя ручка в спеке допустима,
но смонтированная ручка вне спеки — нет. Там же проверяется порядок слоёв: сеанс-гейт
должен покрывать всё после себя, а `POST /api/login` оставаться единственным открытым роутом.

Все даты и времена — **строки**, не `Date`-объекты (`contract/main.tsp`, модель `Meeting`):

```ts
Meeting    { id: string; date: 'YYYY-MM-DD'; time: 'HH:mm' }
MeetingDraft { date: 'YYYY-MM-DD'; time: 'HH:mm' }   // то же без id
DateRange  { from: 'YYYY-MM-DD'; to: 'YYYY-MM-DD' }  // обе границы включительно

MeetingsApi {
  list(range: DateRange): Promise<Meeting[]>    // возрастание по (date, time)
  create(draft: MeetingDraft): Promise<Meeting> // возвращает запись с присвоенным id
}

MeetingType    { id: string; name: string; description: string; active: boolean }
MeetingTypeDraft { name: string; description: string }  // то же без id и active

MeetingTypesApi {                                // src/lib/meeting-types/ (F3), зеркало MeetingsApi
  list(): Promise<MeetingType[]>                 // без параметров: админу — все, гостю —
                                                 // только активные, решает сервер по сессии (S3)
  create(draft: MeetingTypeDraft): Promise<MeetingType>   // новый тип всегда активен
  deactivate(id: string): Promise<MeetingType>            // неизвестный id — исключение
                                                 // (сервер отвечает 400, не 404)
}

PlannedMeeting { date: 'YYYY-MM-DD'; time: 'HH:mm'; type: string | null; booker: string | null }
// S4/Q6: join-DTO, а не Meeting. type — null у легаси-записи без типа, booker —
// null у старой записи без автора (C5); UI рисует оба как «—».

PlannedMeetingsApi {                             // src/lib/planned-meetings/ (S4/F6), зеркало MeetingsApi
  list(): Promise<PlannedMeeting[]>              // без параметров: границу «сегодня и позже»
                                                 // и сортировку date→time держит сервер (Q6)
}

Session     { role: 'admin' | 'guest'; bookerName: string | null }  // у админа bookerName null
LoginInput  { password: string; bookerName?: string } // роль определяет сервер по паролю (Q9, ADR-0006)

SessionApi {                                     // src/lib/session/ (F2), зеркало MeetingsApi
  login(input: LoginInput): Promise<Session>     // неизвестный пароль — исключение (401)
  logout(): Promise<void>                        // без активной сессии — исключение (401)
  me(): Promise<Session | null>                  // 401 — штатное «сессии нет», не ошибка (C9)
}
```

Строки вместо `Date` — по трём причинам:

1. этого требует `DateStringValue` в Mantine v9;
2. `new Date('YYYY-MM-DD')` разбирается как полночь UTC и в отрицательных
   часовых поясах показывает предыдущий день;
3. строки `'YYYY-MM-DD'` лексикографически упорядочены так же, как
   хронологически, поэтому и `inMemory`, и SQLite (`BETWEEN` + `ORDER BY`)
   фильтруют и сортируют без dayjs.

Этот же контракт повторяет HTTP: `id` отдаётся строкой, границы диапазона
включены, сортировка — по `(date, time)`.

Правило доступности дня тоже живёт в `lib` и собирается из трёх независимых
функций: `isPast` сравнивает по дням (`isBefore(…, 'day')`), а не по
точному времени, иначе сегодняшний день считался бы прошедшим в течение суток;
`isWeekend` — суббота и воскресенье; `isBookable` — их отрицание. Все они
принимают «сейчас» параметром (`moment`), а часы читают только `today()` и
`now()` из того же файла — так правило тестируется фиксированной строкой (T3).
Гостевое окно (Q5) собирается поверх в `lib/window.ts`: `isBookableDay` —
будни в пределах сегодня…сегодня+13, `isBookableSlot` — плюс «сегодняшнее
время строго позже текущего». Окно — политика UI, сервер по C1 его не проверяет.

## 5. Решения, за которые пришлось заплатить

**`MeetingCalendar` — единственный компонент со `DatePicker`, а `Calendar`
использовать нельзя.** У `Calendar` нет выделения: `value` / `onChange`
унаследованы от DOM-пропсов корневого `div`, то есть типизированы как свойства
`div` и **молча ничего не делают**, потому что `<div>` не стреляет `change`.
Выделение есть только у `DatePicker`, `DateInput`, `DatePickerInput`.
`DatePicker` рендерит `Calendar` внутри себя, то есть является заменой drop-in.
Правило недоступных дней переворачивается в конвенцию Mantine на месте
(правило — `isBookableDay` из `lib/window.ts`: будни, не прошедший день и
гостевое окно Q5):

```tsx
const moment = now(); // фиксируется на рендер: excludeDate зовётся на каждую ячейку
<DatePicker
  excludeDate={(date) => !isBookableDay(date, moment) || freeCounts?.[date] === 0}
/>
```

**Занятость дней считается в `lib/availability.ts`, а не в компоненте.**
`takenTimesByDay` группирует записи по дням, `freeSlotCounts` обходит окно Q5,
оставляет только bookable-дни и вычитает из `generateTimeSlots()` занятые и уже
начавшиеся сегодняшние слоты (`isBookableSlot`). `GuestView` — единственный
источник этих данных: он считает `freeCounts` и передаёт в `MeetingCalendar`
готовую карту, а компонент только рендерит счётчик (`renderDay`), подпись в
`getDayAriaLabel` («3 октября 2026 — свободно 5») и `title`, плюс
`data-free-count` для тестов. `disabled` в `getDayProps` не передаётся: он
перекрыл бы `excludeDate`; `selected` тоже не трогаем, иначе перекроем выделение
`DatePicker`.

Счётчики считаются только при `loaded`: до первого успешного ответа `meetings`
пуст, а «0 свободных» выключило бы весь месяц. Флаг `loaded` из `useMeetings`
не сбрасывается ошибкой создания (409) — список к этому моменту уже перечитан;
поэтому красный Alert после неудачной записи не прячет счётчики.

**Сетка `TimeSlots` и счётчик календаря берут один список недоступного.**
`unavailableTimes(day, takenTimes, moment)` возвращает занятые слоты плюс уже
начавшиеся сегодня, `freeSlotCounts` считает свободные как
`generateTimeSlots().length` минус длину этого списка. `GuestView` передаёт тот
же список в `TimeSlots`, поэтому «свободно 11» и 11 активных кнопок не могут
разойтись. Если выбранное время стало занятым после «Обновить», `Далее`
блокируется по `selectedTimeAvailable` — подтвердить устаревший слот нельзя.

**Выбор слота — контролируемый пропс `TimeSlots`, состояние в `GuestView`**
(`src/components/TimeSlots.tsx`). Очевидная версия — `useState` внутри
компонента сетки — упирается в `react/set-state-in-effect`: сброс при смене
даты пришлось бы делать в эффекте, а правило его запрещает. Пропс `time`
сбрасывается прямо в обработчике клика по дате (`src/GuestView.tsx`,
`selectDate`), `key`-remount не нужен:

```tsx
onSelect={(date) => { setLastBooked(null); setTime(null); setSelectedDate(date); }}
```

Ступени гостевого вида (F7) устроены так же: `step` — состояние страницы,
«Далее» не даёт перейти дальше без выбора, а `allowNextStepsSelect={false}`
запрещает прыжок на «Готово» мимо даты и времени — назад можно только на
пройденные шаги.

**Первичная загрузка объявлена инлайном в эффекте, а не вызовом `refresh`**
(`src/hooks/useMeetings.ts:79`). Правило `react/set-state-in-effect` срабатывает
**транзитивно**: оно ругается на вызов функции, трогающей состояние, из тела
эффекта — даже если `setState` происходит после `await`. Отсюда флаг `cancelled`:
он же спасает от двойного вызова эффекта в `StrictMode`.

**`lastBooked` — снимок `{ typeName, date, time }`, а не `Meeting`**
(`src/GuestView.tsx`, тип `BookedSummary`). Нужен только для Alert'а «Запись:
…», а у `Meeting` нет ни имени типа (строка должна называть тип, которого в
ответе сервера нет), ни времени создания — «самая свежая» из отсортированного
массива не выводится. Строка ставится только если `createMeeting` вернул
запись (при неудаче — `null`), и сбрасывается сменой любого выбора (типа, даты,
слота) прямо в обработчиках, без эффектов.

**Пропы `api`, `typesApi`, `plannedApi` и `sessionApi` в `App` — не удобство, а
необходимость** (`src/App.tsx`). `lib/meetings/api.ts` экспортирует модульный
синглтон; без подмены записи утекают между тестами одного файла, слот оказывается
`disabled`, `userEvent` кликает по неактивной кнопке, `time` не выставляется, и
тест падает по таймауту `findBy`. Воспроизведено: с синглтоном падает тест
«занятый слот в следующий раз не выбирается». `lib/meeting-types/api.ts` —
синглтон того же вида: с F7 гостевой вид грузит типы сразу после входа, и без
фейка этот запрос в тестах умирает на jsdom-`Request`, а вид красится в ошибку
загрузки. `lib/planned-meetings/api.ts` — такой же синглтон, и админская ветка
грузит список запланированных встреч сразу после входа (F6), поэтому её тестам
нужен `plannedApi`. Тот же аргумент за `sessionApi`: `lib/session/api.ts` —
синглтон того же вида, а приложение целиком закрыто входом (Q12a), поэтому тест
логина обязан подставить свой фейк сессии (T6).

**Дев-обход авторизации — флаг, а не удаление входа** (`server/session.ts`,
`src/lib/devRole.ts`). Чтобы проверять корректность обоих видов, нужен доступ к
ним без пароля — но вырезать аутентификацию значит тронуть контракт, четыре слоя
и ~50 тестов. Вместо этого добавлен режим `AUTH_DISABLED=1`: гейт
`devSessionGate` подставляет сессию, а роль читается из неподписанной cookie
`dev_role`, которую `main.tsx` ставит по URL страницы. Цена — доверие к
клиентской cookie, но лишь в этом режиме: при выключенном флаге `requireSession`
работает как раньше и `dev_role` не читается вовсе. `POST /api/login` в обходе
пароль не сверяет — иначе экран входа после «Выйти» стал бы тупиком.

**Фабрика, а не синглтон, в `inMemory`** (`src/lib/meetings/inMemory.ts:8`) — по
той же причине. Отдельный тест «не делит хранилище между вызовами фабрики»
фиксирует это намерение.

**После конфликта (409) `createMeeting` перечитывает список до показа ошибки**
(`src/hooks/useMeetings.ts`). Если сервер отклонил слот, локальный `meetings`
устарел: чужой занятый слот остался бы визуально свободным. Поэтому в `catch`
сначала `await refresh()`, и только потом `error: CREATE_ERROR` — обратный
порядок стёр бы текст ошибки, потому что `refresh` при успехе ставит
`error: null`.

## 6. Точки расширения

| Задача | Что менять |
| --- | --- |
| Смена хранилища/формата на сервере | Весь сервер за `MeetingsApi` фронта: `meetingsApi` уже указывает на `createHttpMeetingsApi()` (`api.ts:19`); дальше трогается только `server/`. |
| Новая ручка или поле API | `contract/main.tsp` + `npm run contract`: типы приезжают на обе стороны, схема пересобирается для `ajv`, `rootDir` не трогается, дрейф ловит `contract:check`. Роут вне спеки ловит `server/contract.test.ts`. |
| Новое правило формата (поле, паттерн) | `contract/main.tsp` — правило обязано жить в контракте, а не только в серверном коде: валидация идёт по сгенерированной схеме через `ajv` (§4). Рукописной остаётся только то, что JSON Schema не выражает. |
| Правило, зависящее от роли | `server/routes.ts` рядом с `ajv`-предикатом: схема формы роль не выразит (как обязательность `booker` при создании записи — S5). Не подмешивать домен — см. следующую строку. |
| Доменная валидация на сервере (2-й клиент, публичный API) | Сейчас сервер проверяет формат и целостность, но не домен (§4). Правила (`isBookable`, сетка слотов) вынести в общий модуль и звать из `server/validate.ts`; UI продолжит пользоваться `lib/`. |
| Праздники | `lib/date.ts` `isBookable` (день); занятость и полностью занятые дни уже учтены в календаре (§7). |
| Число свободных слотов и полностью занятые дни | `lib/availability.ts` (`takenTimesByDay`, `freeSlotCounts`, `unavailableTimes`): сетка и правила берутся из `lib/slots.ts` и `lib/window.ts`, `GuestView` считает данные, `MeetingCalendar` только рендерит счётчик и выключает нулевые дни. |
| Другое рабочее время | `lib/slots.ts:2-8` (константы) или аргументы `generateTimeSlots`. |
| Горизонт списка записей | `lib/window.ts` `WINDOW_DAYS` (гостевое окно Q5): верхняя граница списка — `windowEnd(now())` в `useMeetings`. Админский список окном не ограничен (Q6): `listPlanned` в `server/repository.ts` фильтрует только «`date >= from`», верхней границы нет (S4). |
| Ручное обновление списка | `refresh` из `useMeetings` (`useMeetings.ts:55`) зовёт кнопка «Обновить» на шаге «Время» в `GuestView`; хук не менялся. |
| Список всех записей (не только сетка слотов) | `GuestView.tsx` получает весь массив `meetings`; сортировка и фильтрация — его дело, а не компонентов. |

## 7. Известные ограничения

Это осознанные решения текущего объёма, а не недосмотры. Каждое — с ценой,
которую полезно знать до начала работы.

1. **Окно считается от текущего момента, а не от отображаемого месяца.**
   Гостевое окно Q5 (сегодня…+13) и граница списка (`windowEnd(now())` в
   `useMeetings`) пересчитываются при загрузке. `MeetingCalendar` может
   показать любой месяц, но за пределами окна дни выключены — туда не загружаются
   и занятые слоты. Админский список окном не ограничен (Q6): `listPlanned`
   берёт всё от `today()` и выше (S4), поэтому записи за пределами 14 дней в нём видны.
2. **Сервер валидирует формат и целостность, но не домен (S5).** Формат
   проверяет `ajv` по схеме из `contract/schema/`, а роуты — целостность:
   названный `meeting_type_id` обязан существовать и быть активным, `booker`
   берётся из подписанной сессии, а не из тела (Q4/C10). Прошедшие даты,
   выходные и время вне сетки слотов сервер принимает — доменная политика
   целиком на фронте (§4, C1). UI такие draft'ы не генерирует
   (`excludeDate` в календаре, `disableTime` в `TimeSlots`),
   поэтому дыра достижима только обходом UI; мусорные записи не показываются
   как занятые. При появлении второго клиента или публичного API — валидировать
   на сервере и домен, вынося правила в общий модуль (§6, ADR-0007).
3. **`AUTH_DISABLED=1` открывает приложение без пароля.** Роль берётся из
   неподписанной cookie `dev_role`, которую ставит клиент по URL, — то есть в
   этом режиме доверие отдано браузеру. Это осознанный инструмент проверки,
   включаемый только конфигом (по умолчанию выключен), и в проде его быть не
   должно. Обычный режим не меняется: роль определяет пароль по подписанной
   сессии (ADR-0006), а `dev_role` без флага не читается.

## 8. Тестовая стратегия

245 тестов: `date.ts` 13, `window.ts` 13, `slots.ts` 4, `availability.ts` 10, `devRole` 1,
`meetings` (`inMemory` 8, `http` 7),
`meeting-types` (`inMemory` 7, `http` 8), `planned-meetings` (`inMemory` 4, `http` 5),
`session` (`inMemory` 8, `http` 10),
`useMeetings` 10, `useMeetingTypes` 6, `usePlannedMeetings` 3, `useSession` 7,
`TimeSlots` 4, `MeetingCalendar` 5 (счётчики, нулевой день, выделение, выходные),
`GuestView` 22 (сценарии букинга F7: тип, слот, подтверждение, Alert'и,
календарь со свободными слотами, «Обновить» и устаревший выбранный слот), `AdminView` 9 (вкладки,
деактивация, создание, легаси-«—», пустое состояние), `App` 8 (сквозные
сценарии гейта по сессии: вход, роль, выход)
— и серверные: `repository` 15 (включая join-DTO `listPlanned`),
`meeting-types-repository` 6, `routes` 44 (матрица доступа anon/guest/admin,
logout T8/Q13, жизненный цикл типа T5/T9, join-DTO `listPlanned`, дев-обход
AUTH_DISABLED),
`contract` 8 (артефакты и статус-коды контракта, сверка смонтированных
роутов со спекой и порядка сеанс-гейта, отсутствие DELETE). Фронтовые тесты
колоцированы в `src/`, поэтому `tsc -b` проверяет их
типы бесплатно; серверные проверяет `tsc -p tsconfig.server.json --noEmit`.

Vitest разведён на два проекта в `vite.config.ts`: `app` (jsdom + `setup.ts`,
`src/**`) и `server` (node, без `setup.ts`, `server/**`). Глобальный `setup.ts`
пишет в `window` — под node-окружением он упал бы, поэтому серверным тестам
он не подключён, а `environment` задан и проектом, и docblock'ом
`@vitest-environment node` на всякий случай.

Серверные тесты собирают приложение как в проде: `createApp({ meetings, meetingTypes }, …)`
на `:memory:`-БД и ходят через реальный `listen(0)` + `fetch` (routes) либо через репозиторий
напрямую (repository, meeting-types-repository). Через `index.ts` не ходят — он биндит порт и открывает
файловую БД. В `repository.test.ts` отдельно проверено, что не-UNIQUE ошибки БД
не маскируются под дубль: подменяется схема на CHECK-ограничение. FK у
better-sqlite3 включены по умолчанию — тест репозитория, ссылающийся на
`meeting_types`, сначала вставляет сам тип.

Требования, каждое из которых уже стоило времени:

- **`MantineProvider` обязателен** в дереве каждого render-теста — Mantine v9
  бросает `MantineProvider was not found in component tree`.
- **Нельзя проверять «сегодня выбирается».** Сегодня может быть выходным, и
  `[data-today]` станет неактивным. Тесты выбирают «первый доступный день
  показанного месяца» (`tbody button:not([disabled]):not([data-outside])`) и
  листают вперёд по `[data-direction="next"]`, если таких нет. Проверки правил
  делаются на `disabled`, а не на конкретных датах.
- **Локаль проверяется по `aria-label` дней**
  (`/^\d{1,2} [а-яё]+ \d{4}( — свободно \d+)?$/`), а не по заголовку месяца:
  заголовок показывает *текущий* месяц, поэтому тест на «октября» зелёный в
  октябре и красный в ноябре.
- **Полностью занятый день выключается через `excludeDate`,** а `disabled` в
  `getDayProps` не передаётся — иначе он тихо перекроет `excludeDate`. Тесты
  проверяют и нулевой счётчик, и сохранение `data-selected` у выбранного дня.
- **Классы в Mantine v9 — `mantine-DatePicker-*`, не `mantine-Calendar-*`.**
  Проверенные: `-weekday` (7 ячеек, lowercase «пн»…«вс»), `-weekdaysRow`,
  `-calendarHeaderLevel`, `-day`, `-monthTbody`.
- **Интеграционный тест обязан передать свой `api`** (обычно
  `createInMemoryMeetingsApi()`, для неудачного создания — заглушку с падающим
  `create`) — см. раздел 5.
- **jsdom не даёт своего `Request`**, глобальным остаётся node'овский (undici), а
  он требует абсолютный URL — в браузере относительный резолвит `location`.
  Поэтому SDK упал бы в `new Request('/api/…')`, не дойдя до fetch, и тесты
  `http.test.ts` подставляют шим `BrowserRequest`, добавляющий ту же основу.
  Это пробел окружения, а не поведение адаптера: прод использует пустой
  `baseUrl` и браузерный резолвинг.

Каждый новый тест проверен мутацией. В F7 харнесс из 21 мутации убил все:
удаление `meeting_type_id` из draft'а валит тест на payload, `if (created !==
null)` → `if (true)` — тест на ошибку создания, `disabled` у кнопки «Далее» —
тест на закрытые переходы. Один выживший (снятие `setLastBooked(null)` из
`selectType`) пойман добавленным тестом «после записи смена типа гасит строку
успеха» — так ловится и «зелёный, но ничего не проверяющий» тест. Раньше то же:
`disabledTimes={[]}` валит тест «занятый
слот в следующий раз не выбирается», удаление `setLastBooked` из
`handleBook` — три теста: два прежних и новый, на сброс строки. Это дешевле,
чем потом отлаживать «зелёный, но ничего не проверяющий» тест. Такая ловушка
уже случалась: тест «create бросает при 400 и 409» проверял лишь `rejects.toThrow()`,
и пока SDK не умел резолвить относительный URL, он проходил на постороннем
`TypeError` из `new Request`. Теперь он сверяет русский текст ошибки. По той же
схеме в K3: удаление `credentials: 'include'` валит тест cookie-сессии, замена
русского текста — тест на 400/409, удаление прокидывания сетевого исключения —
тест на «ошибка сети». В S4/F6 харнесс из 20 мутаций убил 19: `LEFT JOIN` →
`INNER JOIN` валит тест на легаси-строки, `requireRole('admin')` → `guest` —
матрицу 403, `today()` → фиксированное прошлое — тест «сегодня в списке»,
снятие `disabled={!type.active}` и `checked={type.active}` — тесты деактивации,
`meeting.type ?? '—'` — тест легаси-прочерков, отключение `refresh` в
`usePlannedMeetings` — тест перечитывания. Один выживший эквивалентен: удаление
`ORDER BY m.date, m.time` поведения не меняет — `UNIQUE(date, time)` создаёт
автоиндекс, и `WHERE m.date >= ?` уже отдаёт строки в порядке (date, time);
строка оставлена страховкой от смены плана.

Дев-обход (AUTH_DISABLED) закрыт харнессом из 5 мутаций — все убиты: замена гейта
на `requireSession`, cookie `dev_role=admin` без роли admin, снятие ветки login в
обходе, возврат обязательной проверки auth-конфига в `createApp` и расширение
`/admin` до `startsWith('/admin')` (ловит `/administrator`).

Счётчики свободных слотов и ручное обновление закрыты харнессом из 11 мутаций —
все убиты: снятие суффикса из `getDayAriaLabel` (6 падений), удаление `title` (1),
удаление `data-free-count` (2), игнорирование счётчика в `renderDay` (1),
`undefined` → `0` (4), расчёт счётчиков при загрузке (2), гейт по `error` вместо
`loaded` (2), `Далее` без проверки занятости выбранного времени (1),
`unavailableTimes` без `isBookableSlot` (3), `freeSlotCounts` без того же правила
(2) и старый ответ загрузки, перезаписывающий свежий `refresh` (1). Визуальная
приёмка ячейки: в headless Chrome ячейка 36×36, `scrollHeight` 36 при
`overflow: visible`, содержимое 26px; у дня «свободно 17» сетка показала ровно
17 активных слотов, а занятый 17:00 был выключен.

`npm run preview` — только проверка собранной статики: `/api` она не знает,
поэтому записи не грузятся.

`npm run dev` **не даёт обратной связи по типам** (ни фронт, ни сервер): Vite
и `tsx watch` вырезают типы, не проверяя их. Для проверки типов в разработке —
`npx tsc --noEmit -p tsconfig.app.json --watch` и
`npx tsc --noEmit -p tsconfig.server.json --watch` во втором терминале.

Линтер — `oxlint`, не ESLint. В `.oxlintrc.json` категории `correctness` и
`suspicious` это `error` и роняют код выхода, `perf` — `warn`, поэтому текущие
warning `react-perf` на инлайн-обратчиках и свежих массивах `disabledTimes` падением
не считаются. `unicorn` в `plugins` отсутствует и потому выключен: `plugins`
заменяет набор по умолчанию, а не дополняет его.
