# Слот — глобальный разделяемый ресурс, а не занятость по типу

Календарь — фиксированная получасовая сетка рабочих дней (`src/lib/slots.ts`). Её можно смоделировать как занятость **по типу** (одно и то же время занимается отдельно под каждым типом встречи) или как **один глобальный ресурс** (слот свободен или занят независимо от типа). Решили второе: `UNIQUE(date, time)` на таблице `meetings`, на один слот — максимум одна встреча по всем типам. Причина доменная: календарь предлагает один админ — один человек, — и две его встречи в одно время физически невозможны, какого бы типа они ни были.

## Considered Options

- **Занятость по типу** (`UNIQUE(date, time, meeting_type_id)`) — отклонено: позволило бы одному админу быть занятым дважды в один момент, если один гость выбрал один тип, а другой гость — другой.
- **Глобальный `UNIQUE(date, time)`** — выбрано.

## Consequences

- **Свободные слоты = сетка − занято.** Сетка статична (`src/lib/slots.ts`), занятость приходит из `GET /api/meetings?from&to`; матрицы доступности по типам нет.
- **Инвариант держит БД, а не приложение.** `UNIQUE(date, time)` сохраняется миграцией C2 (S1: легаси-таблица `bookings` переименовывается в `meetings`, строки и ограничение переживают `ALTER TABLE RENAME`), а дубль превращается в `DuplicateMeetingError` → **409** (T4).
- **Смена решения — это схема плюс контракт.** Переход к ёмкости по типу (или нескольким встречам на слот) меняет модель `Meeting` и ручки `/api/meetings`; поэтому решение зафиксировано.
